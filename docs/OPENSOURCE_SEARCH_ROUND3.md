## 二、各項目深挖結論

### 1. xue-lpd（MTCNN + LPRNet + STN）—— 有一個值得抄的點

**架構**：
```
MTCNN（簡化：只用 Pnet + Onet，跳過 Rnet）
    ↓ 輸出車牌框
LPRNet + STN（空間變換層自動對齊）
    ↓ 輸出字符序列
```

**STN 實測（本次實際跑出來的）**：

```python
STN (SpatialTransformer)  params=55,430  (216.5 KB fp32)
輸入 (1,3,24,94) → 輸出 (1,3,24,94)   # 形狀不變，內容自動對齊
```

實現原理（`STN.py`，56 行）：

```python
# localization: 兩層 Conv 提取特徵
Conv(3→32,k3) → MaxPool(2,2) → ReLU → Conv(32→32,k5) → MaxPool(3,3) → ReLU
# regressor: 回歸 2×3 仿射矩陣
Linear(896→32) → ReLU → Linear(32→6)
# 初始化為恆等變換，訓練時學偏移
fc_loc[2].bias = [1,0,0, 0,1,0]
# 應用
grid = F.affine_grid(theta, x.size())   # theta: [B,2,3]
x = F.grid_sample(x, grid)
```

**價值評估**：⭐⭐⭐⭐

| 優勢 | 說明 |
|------|------|
| 不依賴檢測器關鍵點精度 | 現在我們靠 4 角點透視，角點偏了識別就崩 |
| 端到端可訓練 | 與識別網絡聯合優化 |
| 極輕量 | 55K 參數，僅為識別器的 31% |
| 對小角度歪斜魯棒 | 網絡自動學到校正 |

**局限**：
- 仿射變換只能做平移/旋轉/縮放/剪切，**不能做完整透視**（梯形→矩形）
- 需要足夠數據訓練才能學好，初期可能不如手工透視

**建議**：作為**可選增強**加入。先用手工透視（可靠），等數據充足後可加 STN 讓網絡自己學微調。

### 2. zxx-lpd（畢業設計）—— 排除

**發現的三個問題**：

**問題 1：代碼不完整**
`read_plate.py` 導入 `from ocr_explorer import Explorer`，但倉庫裡**沒有 ocr_explorer.py**。核心識別模組缺失，無法運行。

**問題 2：仿射參數化角點是退步，不是進步**

```python
# detect_explorer.py:60 — 從 grid cell 回歸 2×3 仿射矩陣
affines = torch.cat((predict[0,:,:,2:3], ..., predict[0,:,:,7:8]), dim=2)
affines = affines.reshape(h, w, 2, 3)
# 乘單位方塊 4 點
unit = [[-0.5,-0.5,1],[0.5,-0.5,1],[0.5,0.5,1],[-0.5,0.5,1]].T
pts = affine @ unit
```

用仿射參數化 4 角點的後果：**只能表示平行四邊形**。
但車牌在透視下是**梯形**（近大遠小）。所以這個表示法**先天無法準確描述車牌**。

我們直接回歸 8 個座標值（`landmarks`），可以表示任意四邊形（含梯形），**更準確**。

**問題 3：生成器同樣是字體渲染**

```python
# kenshutsu.py:95
font = ImageFont.truetype("MSJHL.TTC", fontSize, encoding="utf-8")
```

用華文隸書字體渲染車牌 —— 跟我們犯的錯誤一模一樣。

**結論**：❌ 排除。唯一可借鑒的是「用程序生成車牌補充數據」的思路（但方法本身已被 `cn-plate-generator` 的真實貼片法超越）。

### 3. yolo26-plate（we0091234 最新版）—— 一個真改進 + 一個假改進

#### 真改進：檢測改用 YOLO Pose 任務 ⭐⭐⭐⭐

```yaml
# cfg/plate.yaml
kpt_shape: [4, 2]        # 4 個關鍵點，2 維 (x,y)
flip_idx: [1, 0, 3, 2]   # 水平翻轉時關鍵點交換順序
names:
  0: single
  1: double
```

**為何這是好設計**：
- Pose 任務天生輸出「框 + 關鍵點」，正好對應車牌的「邊框 + 4 角點」
- 不需要像 v5 版那樣在檢測頭裡手工塞 8 個座標通道
- Ultralytics 已充分優化 pose 的訓練/導出/部署鏈路
- `flip_idx` 自動處理水平翻轉增強時關鍵點順序（細節但關鍵：翻轉後左上↔右上）

**這是我們應該採用的**。

#### 假改進：其餘部分

| 號稱 | 實際 |
|------|------|
| 主入口 422 行 | 其中 **~250 行是繪圖美化**（`_draw_glow_border` / `_draw_tech_box` / `_measure_text` / `_fit_font_size` 等 14 個函數），核心推理僅 ~120 行 |
| 有 tests/ | 是 ultralytics 自帶的 `test_cuda.py` / `test_engine.py` / `test_python.py`，**無一個車牌專屬測試** |
| 有配置化 | `cfg/plate.yaml` 洩露作者私有路徑 `/mnt/xiaolei2/detect/640_plate_lands`，非通用配置 |
| 識別升級 | `plate_recognition/` 三個文件**與 v5 版逐字相同**（15 + 202 + 119 行）|
| 類別 | 依然 `single` / `double`，**無地區分類** |

**結論**：✅ 只採用「Pose 任務做檢測」這一點。其餘不採用。

## 三、意外發現：識別輸入長寬比

| 項目 | 識別輸入 | 長寬比 |
|------|---------|--------|
| GBA / yolo26 | 168×48 | **3.5 : 1** |
| xue-lpd / HuKai97 | 94×24 | **3.9 : 1** |
| zxx-lpd | 144×48 | **3.0 : 1** |
| **車牌實際標準** | 440×140mm | **3.14 : 1** |

zxx-lpd 的 144×48 最接近真實比例，我們的 168×48 偏扁（字符被橫向拉伸 11%）。

**影響評估**：CRNN 訓練時已適應 168×48，所以推論沒問題。但如果重訓識別器，改成 **150×48（3.125:1）** 或 **144×46** 會更貼近物理比例。

**暫時不動**，等重訓時再調整。

## 四、第三輪結論

### 採用

| 來源 | 採用什麼 | 理由 |
|------|---------|------|
| **yolo26-plate** | 檢測改用 **YOLO Pose**（`kpt_shape: [4,2]` + `flip_idx`）| 4 角點原生支援，鏈路成熟 |
| **xue-lpd** | **STN 模組**（55K 參數）作為可選對齊增強 | 不依賴角點精度，端到端可學 |

### 排除

| 項目 | 理由 |
|------|------|
| zxx-lpd | 代碼不完整（缺核心識別模組）+ 仿射參數化無法表示梯形 + 生成器同樣字體渲染 |
| xue-lpd 的 MTCNN | 2016 年方案，80ms/image 過慢，遠不如 YOLO |
| yolo26-plate 其餘 | 60% 繪圖代碼、識別零改動、無地區分類、無專屬測試 |

### 確認

三個項目**全部沒有地區分類**（都是 single/double 兩類）。
→ 我們的 4 類別改造（mainland/gangao/hk/mo）**沒有現成方案可抄，是獨創部分**。
